The question that crosses areas

"Billing and complaints by region and month, in one table"

  • Two facts at different grains: one bill per account and month; one row per complaint
  • Two calendars to agree on: service month for bills, opening day for complaints
  • Two regions to choose between: the customer's, or where the complaint was raised

What the layer must guarantee

Each figure is the same as it would be alone, whatever it is shown beside.

Use one of the participants' own cross-area questions here. Ask which grain each fact has. The last bullet is a real design decision that comes back in session 3: the regional manager's complaints are those raised in the region.

The join meets one row per key on each side, so nothing repeats. It needs every area to reach the same customer and calendar: conformed dimensions.

Show the generated SQL in the lab: two CTEs, then a FULL JOIN USING the keys. MetricFlow and Cube do the same for metrics from different models. In the starter model, complaints have no join to the customer and no calendar, so the layer refuses: "no many-to-one path from complaint to customer". A refusal is better than a wrong number.

The evidence for the first outcome

A model is done when its parts add up to the source, area by area

  • One reconciliation test per area: usage, billing, collections, complaints
  • Regions add up to the total for the billed amount; plans add up to the total for data
  • Run in CI with the metric tests, so a model change that breaks a total cannot merge
Totals are the minimum. A split that does not add up (by plan before the as-of join) is a test worth keeping.

The capstone's rubric gives 30 points to the semantic model and metrics; "model files whose reconciliation tests pass against source totals" is the evidence the entry names. Encourage tests by the dimension that has a history or a fan-out risk.

What a pre-aggregation is

A pre-aggregation stores additive measures at a coarser grain, and the layer routes to it

Additive only

Sums and counts. A ratio uses its stored numerator and denominator.

Covers the query

Every group-by and filter field of the query is among its fields.

Same answer

Routing changes the cost, never the number. Test that.

Cube calls them pre-aggregations; other tools call them aggregate tables, rollups or materialized views. The routing rule in the course layer is in qsem.py (_preagg_for): same dataset, measure stored, query fields a subset, additive aggregate.

Lab 2.3, step 2

Test every role against every area, by asking as that role

for role, r in policy["roles"].items():
    m = model.as_role(role, policy=policy)
    for area, (metric, region) in AREAS.items():
        seen = set(m.query([metric], by=[region])[region])
        passed = r["regions"] == "all" or seen <= set(r["regions"])
    for field in ("customer.full_name", "customer.contact_name"):
        masked = set(m.query(["billed_amount"], by=[field])[field]) == {"***"}
        passed = masked != r["restricted"]

21 tests: 3 roles times (5 areas plus 2 fields). A test asks the layer the way a dashboard or the assistant would, and checks what came back. Point at the last line: a role with clearance must see the values, so the test also catches over-masking.

Lab 2.3, step 3

Three of 21 tests fail, and they point at two leaks

A dataset without a rule

The Eastern manager sees complaints of all five regions: 612 in the Central region alone. The policy has no rule for complaint, and the layer allowed by default.

A copy without its label

contact_name takes the first word of full_name. Nobody tagged it, so the executive and the manager read first names.

From Lab 2.3. Both leaks are common in practice: a new area added after the policy was written, and a derived field created for a friendly greeting. Ask the room which one an audit of the policy file would have found (the first) and which only a test finds (the second).

Lab 2.3, step 4

Fix the cause: a rule per dataset, deny by default, classify by lineage

Open interchange

Definitions written once should outlive the tool that serves them

  • Apache Ossie (incubating), formerly Open Semantic Interchange: one YAML or JSON document per model
  • Datasets, fields, relationships and model-scoped metrics; AI context such as synonyms
  • The core specification is a draft, 0.3.0.dev0: expect changes

From DS-307

You wrote a first model in this format. Today you export a whole layer and run it somewhere else.

Sources: the Apache Ossie announcement of its entry into the Apache Incubator, and the core specification on GitHub (spec.md), read for this course. The project publishes converters for dbt, Cube and others; check their status before relying on one. The status of the specification is in the entry's refresh list: re-check it before each cohort.

  - name: collection_rate

      sql: (SUM(CASE WHEN collection.matured_30 THEN collection.paid_30 END)) * 1.0

There are no metric types in the core: a ratio is written out as SQL, which is why exporting needs a translation step. 24 metrics exported; the cumulative one (cash collected to date) stays behind because the core has no window over time. The service_month expression is the planted portability problem.

Lab 2.4, step 5

Definitions travel; governance and some logic stay behind

  • Access rules and roles: not in the core at all
  • Classification of fields, the as-of tariff join: vendor extensions only
  • The cumulative metric, and MEDIAN, which SQLite lacks
  • Two datasets defined as DuckDB queries: materialized as tables first
Moving tools moves the risk. The access tests of Lab 2.3 must be carried and re-run on the new tool by hand.

Logic every engine must share belongs in the transformation framework (SQLMesh, dbt), built once as tables; the semantic layer then only names and combines. This is the portability lens of the design review on Day 4.
